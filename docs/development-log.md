# Development log

One entry per working session or delivered story, newest first. What was decided lives in
[requirements.md](requirements.md) and [algorithm.md](algorithm.md); this is the record of how it got
there.

| # | By | Focus | Outcome | Changed course on |
| - | -- | ----- | ------- | ----------------- |
| 7 | Developer + AI | Cost generator | A single chronological sweep: 1–10 attempts a day at distinct random instants, each cost drawn from the headroom remaining at that moment, so both caps hold by construction rather than being checked afterwards. Pause, daily overspend and monthly exhaustion collapse into one expression — `min(2 × budget − spent today, allowance − spent this month)`, refused when not positive — so there is no special case for a paused campaign anywhere in the generator. Randomness is a seeded `Xoshiro256StarStar`, never global `mt_rand`: 140 tests and 100k assertions sweep the invariants across many seeds and randomly generated histories, and every failure message carries the seed that produced it. | Left a known artefact in place rather than fixing it. The caps are asymmetric — the daily rule permits twice the budget while the month permits only its sum — so drawing freely from the headroom empties a month in about half its days: a constant budget of 10 spends its entire 310 allowance by the 17th and generates nothing for the remaining fortnight. That follows from the rules as written, so it is asserted by a test rather than quietly smoothed away. |
| 6 | Developer + AI | Monthly allowance | `MonthlyAllowance::at(t)` — rule 2's ceiling as known at the instant a cost is generated: elapsed days at their maximum in effect, today at the high-water mark it has reached, and the days still to come projected at the current budget. Recomputed on every call rather than cached; it is at most 31 additions, and an incremental version would be easy to get subtly wrong. Converges to `31 / 20 / 31` for the exercise's history once each month is over. | The test that matters asserts a property inspection cannot: evaluated at a given instant, the allowance is identical across histories that agree up to that instant and diverge afterwards — whether the user later raises the budget to 500 or pauses entirely. Without it, "generation only sees the past" is a claim rather than a guarantee. |
| 5 | Developer + AI | Domain foundations | The value objects the exercise is built from, as framework-free PHP in `api/src/Domain`: `Money` in integer cents, `BudgetChange`, `BudgetHistory` with carry-over lookup, `Period`, and `BudgetTimeline` computing both daily maxima. 44 unit tests, none of which boot a kernel. The PHPUnit suite is now split into `unit` and `functional`, which became meaningful once there was something to unit-test. | `budgetAt` returns null before the first budget change rather than zero — the campaign has not started, which is a different statement from a budget of zero even though both generate nothing. Likewise `maxBudgetSet` is null on a day the user touched nothing; showing the carried value instead is the report's decision and stays out of the domain. |
| 4 | Developer | CI/CD | GitHub Actions running the same gates as local development, and the same commands: `composer validate`, formatting, PHPStan at level max, service-container and YAML linting, PHPUnit and `composer audit` on the API; type-check, ESLint, Prettier and Vitest on the frontend. A third job builds both images, starts the stack, waits for its health checks and curls the API, the frontend and the proxied endpoint — a green test suite says nothing about whether `docker compose up` still works. One aggregating check for branch protection, Dependabot across all three ecosystems, and a tag-triggered workflow publishing images to GHCR. Every job invokes `make` targets rather than repeating the commands, so the Makefile is the single definition of what "checked" means and CI cannot drift from local development. | Placed CI second rather than last: a pipeline added at the end only ever verifies the final commit, whereas this one verifies every story as it lands. No deploy step — there is no environment, and a stubbed one would be worse than its absence. First draft duplicated every command in both the workflow and the Makefile — the very drift the Makefile existed to prevent — so CI now calls the targets instead. |
| 3 | Developer + AI | Application skeleton | Symfony 7 on the minimal skeleton and a React 19 / Vite frontend, running together under `docker compose up`, with a `GET /api/health` endpoint the UI displays and re-checks on demand. Quality gates in place before any behaviour: PHPStan at level max with no baseline, PHP-CS-Fixer, ESLint strict-type-checked with `no-explicit-any` as an error, TypeScript strict with `noUncheckedIndexedAccess` and `exactOptionalPropertyTypes`, and both test suites wired and passing. | Started with php-fpm behind nginx out of habit and replaced it with FrankenPHP, which serves the application directly — php-fpm does not speak HTTP, so choosing it had forced a second container and a FastCGI config that were doing nothing this application needs. Host ports also moved off the conventional 5173 and 8080, which were already taken on the development machine, and are overridable through `WEB_PORT` and `API_PORT`. |
| 2 | Developer | Input format, and how much state to keep | The budget history is a CSV. The server is stateless: `POST /api/simulate` takes an uploaded CSV and a seed and returns the costs and the report, `GET /api/sample` serves the example. No in-app editing of budget changes — download the example, edit it in a spreadsheet, upload it. | Dropped MySQL, then dropped the in-memory working copy that briefly replaced it. The database had been chosen before the input format was settled, and its real job was storing named scenarios — which a CSV file already does. Keeping a server-side copy so the UI could edit it was the same mistake one size down: state nobody asked for, and PHP-FPM would have needed a shared backing store for it to survive a request at all. |
| 1 | Developer + AI | Reading the specification | Dates are `MM.DD.YYYY`. Budgets carry forward until the next change. The daily cap is evaluated at the moment of generation and never rolls back. The report shows the budget the user *set*; rule 2 sums the budget *in effect* — two requirements, two quantities. The allowance is recomputed at each attempt from what is known then, never from future budgets. One refusal rule covers pause, daily overspend and monthly exhaustion. 1–10 attempts per day at uniform moments. Stack: Symfony 7 + MySQL 8 + React, algorithm as framework-free PHP. | Read the example as self-contradictory on 01.05 — it is not; the contradiction only appears if budgets reset daily, which the example disproves. Which maximum rule 2 sums, twice: first on a wording argument that was too thin, then back on example evidence that turned out to be about the report rather than the allowance. Computing the allowance up-front from the full history, before recognising that generation must only ever see the past. |
